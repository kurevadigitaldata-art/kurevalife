# Validación final integral — KurevaLife

**Fecha de auditoría:** 12 de septiembre de 2026
**Fuente de verdad:** `https://github.com/kurevadigitaldata-art/kurevalife`, rama `main`, línea base conservada en `a0967fb4abca8407c6e8124f63859f81647cf17c`.
**Ruta evaluada:** `/vida`.

> **Decisión de aceptación:** el simulador local-first supera la validación técnica, funcional y visual reproducible descrita en este documento. **No se autoriza todavía la distribución a testers desde el enlace de GitHub Pages documentado**, porque dicho sitio no existe actualmente (`HTTP 404`; API pública del repositorio: `has_pages: false`) y la protección RLS del buzón externo no puede verificarse con permisos administrativos. Ambos son bloqueos externos y no se han ocultado como conformidad.

## 1. Alcance y fuente de verdad

Esta auditoría se realizó exclusivamente sobre el repositorio canónico clonado en `/home/ubuntu/workspaces/kurevalife`. Se preservó la versión funcional del simulador y la mejora de Kivi del commit de referencia. No se creó una aplicación nueva, no se rediseñó la interfaz y no se eliminaron datos ni trabajo válido. La comprobación anterior que presentaba siete destinos principales pertenece a un estado histórico anterior: el commit de referencia ya contenía la barra inferior obligatoria **Hoy, Registrar, Informes y Perfil**, con Kivi como control secundario en la cabecera.

La aplicación continúa siendo un simulacro local-first. Los registros, rutinas, avisos, preferencias, hidratación y preguntas se conservan en el navegador; no se convierten en una cuenta, no se sincronizan y no se interpretan clínicamente. La exportación PDF se hace en el dispositivo. Las pruebas de feedback se realizaron interceptando las solicitudes de red, de modo que no se insertó una valoración ficticia ni se enviaron datos de prueba al buzón real.

Se verificó Prettier sobre los archivos modificados sin desviaciones heredadas, el compilador TypeScript, el diff y las suites de navegador disponibles. `Calculator.tsx` ya contenía diferencias de Prettier fuera de las dos líneas corregidas; se conservó su formato existente para no reescribir trabajo válido y `git diff --check` confirmó que el cambio introducido no tiene defectos de whitespace.

## 4. Accesibilidad, identidad y rendimiento

La revisión visual se realizó con capturas de Hoy en móvil, Informes en escritorio y Perfil en modo nocturno. La superficie crema, tarjetas claras, Bosque, Musgo y Lima se mantienen sin añadir estética o funcionalidades nuevas. La navegación inferior conserva los cuatro destinos requeridos y no cubre acciones primarias. Kivi se mantiene como asistente de cabecera, no como quinta pestaña. La exploración pública temporal sin alias también abrió correctamente el simulacro.

La comprobación estática del simulador no encontró referencias a pulso, respiración, rebote ni iconos clínicos prohibidos dentro de `KurevaLifeApp` y `components/kurevalife`. La marca conserva únicamente la rotación ornamental y respeta `prefers-reduced-motion`. Las etiquetas de formularios siguen asociadas a sus controles, los estados importantes usan `aria-live` o `role=status`, se conserva el enlace de salto y Kivi recibe foco al abrirse.

La división de rutas y de PDF eliminó el aviso de chunks de más de 500 kB. La librería PDF no se descarga al abrir KurevaLife: se carga solo al pedir una exportación. Se conservó la confirmación humana si, excepcionalmente, el PDF no se puede preparar, y los datos locales no se descartan.

## 5. Bloqueos externos y procedimiento manual verificable

| Bloqueo                  | Estado verificable                                                                                                                                                      | Impacto en la autorización                                                                                     | Acción manual necesaria                                                                                                                                                                                                                                                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GitHub Pages             | El 12 de septiembre de 2026, `https://kurevadigitaldata-art.github.io/kurevalife/vida` devolvió `HTTP 404`; la API pública del repositorio indicó `has_pages: false`.   | **Bloquea** distribuir el enlace de GitHub Pages a testers.                                                    | Una persona administradora del repositorio debe habilitar Pages con fuente **GitHub Actions** en Settings → Pages y ejecutar el workflow desde `main` o `workflow_dispatch`. GitHub indica que los custom workflows requieren que Pages esté habilitado en el repositorio. [1] |
| Permisos RLS de Supabase | No existe un conector o credencial administrativa disponible en esta sesión. La clave pública del cliente no acredita aislamiento de lectura ni políticas de inserción. | **Bloquea** afirmar que el buzón privado y cualquier comunidad remota están protegidos de forma independiente. | Un administrador de Supabase debe revisar y registrar las políticas RLS de `pilot_feedback`, `pilot_interest`, `pilot_community_messages` y `pilot_windows`, verificando que no existan lecturas públicas de datos privados.                                                   |
| Activación del workflow  | El workflow está corregido, pero no se ha enviado al remoto desde esta sesión y no existe autenticación GitHub disponible para hacerlo.                                 | Impide comprobar una ejecución real de Actions o activar Pages desde esta auditoría local.                     | Enviar el checkpoint al repositorio canónico y revisar el resultado del workflow. El uso oficial de `configure-pages`, la carga del artifact y `deploy-pages` está documentado por GitHub. [1]                                                                                 |

No se debe utilizar la URL temporal de auditoría como enlace del piloto: su disponibilidad es transitoria. La decisión de “apta para testers” solo puede emitirse cuando el enlace oficial devuelva 200 tras el despliegue y la revisión RLS haya sido acreditada. Hasta entonces, el simulador queda **aceptado técnicamente de forma condicionada, pero no autorizado operativamente para testers**.
